# `rpcbind` decoded data

Transport: TCP and UDP. Shared encodings and frame fields are described in [Logging and producers](../logging.md#decoded-data).

**`decoded`:** Array of per-direction frames: `direction`, `command`, `xid`, `program`, `version`, `procedure`, `auth`, `machine_name`, `uid`, `gid`, `target_program`, `target_version`, `netid`, `status`, `payload`, `truncated`

ONC RPC portmapper / rpcbind (program 100000, RFC 1833) on tcp/111 and udp/111. The `tcp` catch-all also routes a record-marked RPC v2 CALL (single last fragment) on any other port here, so scanners probing RPC services on moved ports get a `PROG_UNAVAIL` reply instead of random bytes. Over TCP, each message is record-marked (RFC 5531 §11): `payload` keeps the 4-byte marks, fragments are reassembled up to 16 KiB (`truncated` past the cap, which ends the session), and up to 32 calls are answered per connection (`endReason` `max_frames` after that). Over UDP, one datagram is one event, capped at 1024 bytes; a truncated datagram is recorded but not answered.

Read frames: `command` is `PMAPPROC_NULL|SET|UNSET|GETPORT|DUMP|CALLIT` for version 2, `RPCBPROC_*` (`GETADDR`, `DUMP`, `GETTIME`, `GETVERSADDR`, …) for versions 3 and 4, `CALL` for a call to any other program, `REPLY` for an RPC reply, and `UNKNOWN` when not even a call header could be recovered. `xid`, `program`, `version` and `procedure` come from the call header; `auth` is the credential flavor (`AUTH_NONE`, `AUTH_SYS`, …), and an `AUTH_SYS` credential adds the client's `machine_name`, `uid` and `gid`. SET, UNSET, GETPORT, GETADDR and GETVERSADDR set `target_program`, `target_version` and `netid` (`tcp`/`udp` for a v2 protocol number). A call truncated before the auth verifier (for example a 32-byte UDP datagram that stops after an empty AUTH_NONE credential) still records those header fields and a best-effort `command`, but is not answered.

Write frames echo `command` and `xid` and set `status` to the RPC outcome: `SUCCESS`, `PROG_UNAVAIL` (any program other than 100000), `PROG_MISMATCH` (versions 2–4 supported), `PROC_UNAVAIL`, `GARBAGE_ARGS`, or `RPC_MISMATCH` (RPC version other than 2). The registered services are those of a plausible NFS server: rpcbind v4/v3/v2 on port 111 (TCP and UDP), `nfs` (100003) v3/v4 on the canonical 2049, and `status` (100024, rpc.statd), `mountd` (100005) and `nlockmgr` (100021) on ports derived from the sensor address, so sensors do not share one port set. `DUMP` lists them (v2 `pmaplist`, v3/v4 `rpcb` entries with universal addresses `0.0.0.0.p1.p2`); `GETPORT`/`GETADDR` return the port or address of a registered program (any version, like rpcbind's `find_service`), or `0`/empty. `SET`/`UNSET` return false, as rpcbind does for non-local callers. `CALLIT` (procedure 5) and `INDIRECT` (v3/v4 procedure 10) capture the relayed call's `target_program`/`target_version` on the read frame but are **never forwarded**; like a real rpcbind whose target does not answer, they get no reply (no write frame). UDP replies go only to the datagram source and are charged against `udp_reply_limit`; a v2 `DUMP` reply is about 500 bytes for a 40-byte call.
