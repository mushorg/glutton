# `tcp` decoded data

Transport: TCP. Shared encodings and frame fields are described in [Logging and producers](../logging.md#decoded-data).

**`decoded`:** Array of per-direction frames: `direction`, `command`, `status`, `payload`, `payload_hash`, and on `tls-clienthello` / `tls-alert` reads `tls_version`, `cipher_suites`, `extensions`, `groups`, `sni`, `alpn`, `ja3`, `ja4`

Catch-all. Each client message is one `read` frame (capped by `max_tcp_payload`) and gets one reply, for up to 4 messages per connection; the handler then hangs up with `endReason` `max_frames`. It also hangs up after a reply that ends the session on a real service (`http`, which sends `Connection: close`) or a silent one. A client that closes after a reply ends with `client_close` (or `timeout` when it goes quiet), since the handler waits for a next message. The reply is a canned service response (`protocols/tcp/banners`, from honeytrap per mushorg/glutton#53): a payload signature wins (`SSH-` → `ssh` banner, TLS record → `tls-alert` unless it is a complete ClientHello, see below; HTTP/2 client preface `PRI * HTTP/2.0` (h2c prior knowledge) → `http2-settings`, an nginx-style SETTINGS, WINDOW_UPDATE, SETTINGS ACK and GOAWAY (NO_ERROR) on stream 0; X11 connection setup → `x11-denied`, a setup Failed reply "No protocol specified" in the client's byte order; LDAP root DSE search (empty base, scope baseObject) → `ldap-rootdse`, an OpenLDAP-style SearchResultEntry plus SearchResultDone echoing the messageID; `MGLNDD_<ip>_<port>` scanner probe → `mglndd`, no reply) and sets `command` on the read. A complete ClientHello is tagged `tls-clienthello` instead: the handler finishes the handshake with the shared self-signed certificate (`helpers.TerminateTLSFrom`), sets the event's `tls` object, and answers the next decrypted client message exactly like a plaintext first message (signature, then port response, then random bytes); a server-first port banner is sent inside the tunnel right after the handshake. Those frames hold plaintext. A client that hangs up during or right after the handshake leaves only the `tls-clienthello` read. A `tls-clienthello` read (and a `tls-alert` read that still parses) carries the hello's fingerprint (`helpers.ParseClientHello`, which uses crypto/tls's parser): `tls_version` is the highest offered version; `cipher_suites`, `extensions` and `groups` are decimal code points in wire order with GREASE kept; `sni` and `alpn` appear only when sent; `ja3` is the JA3 MD5 and `ja4` the FoxIO JA4 string. A truncated or malformed record has none of these fields; otherwise the destination port picks it (80 `http`, 135 `dcerpc-bind-ack`, 139 `netbios-session`, 1433 `mssql-prelogin`, 4444 `cmd-shell`, 4899 `radmin`, 8009 `ajp-404`, 8126 `statsd-stats` (an Etsy statsd management console `stats` block ending in `END\n\n`, with uptime and `last_*` deltas from the clock); 389 `ldap` sends nothing, as an LDAP server does with input it cannot parse); otherwise random bytes. Silent responses (`mglndd`, `ldap`) leave only the `read` frame, with no `write`. Writes set `status` to the response name or `random`. Ports 22/2222 (`ssh`), 110 (`pop3`) and 5900 (`rfb`) get their banner on connect, before any read. Port 4444 (`cmd-shell`, a Windows Server 2003 `cmd.exe` prompt) waits 2s for the client first: a silent client gets the prompt as `decoded[0]` (a `write`), a client that speaks first is routed by its bytes as on any catch-all port (HTTP to `http`) and otherwise gets the prompt as the reply. After a greeting, the client's messages get random bytes unless a payload signature matches (no shell is emulated). On 5900 a valid RFB ProtocolVersion reply is tagged `command` `rfb` and answered with the security handshake (`status` `rfb-security`: `02 02 01` for 3.7/3.8, `00 00 00 02` for 3.3) instead of random bytes; the `rfb` handler (routed by default) takes the session further. Clients that send nothing get no reply. RDP X.224 Connection Requests (any cookie length) never reach this handler: the catch-all routes them to `rdp` on any port. Older sensors routed only 43-byte CRs, and only with Spicy enabled; other off-port CRs got `random` writes, which is a handler artifact.
