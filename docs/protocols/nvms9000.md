# `nvms9000` decoded data

Transport: TCP. Shared encodings and frame fields are described in [Logging and producers](../logging.md#decoded-data).

**`decoded`:** Array of per-direction frames: `direction`, `command`, `command_id`, `username`, `password`, `status`, `payload`, `truncated`

TVT NVMS-9000 DVR/NVR management protocol (tcp/6036). The frame layout is inferred from one captured `queryBasicCfg` request (Ochi event `8c21d002-4069-4f48-a464-ac3eb5742229`, tcp/8888), not from a spec:

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | magic `1111` |
| 4 | 4 | LE length of everything after this field |
| 8 | 4 | version/flags (`04 00 00 01`) |
| 12 | 4 | LE command id (`0x091b` on `queryBasicCfg`) |
| 16 | 4 | unknown (`02 01 00 00`) |
| 20 | 4 | LE body length |
| 24 | 64 | user name, NUL padded (`admin`) |
| 88 | 64 | operation name, NUL padded (`queryBasicCfg`) |
| 152 | rest | XML document (`<request version="1.0" systemType="NVMS-9000" clientType="WEB"/>`) |

- `command` is the operation name from the second 64-byte field; `command_id` is the header command id. `username` is the first 64-byte field. When the XML carries `userName`/`password` elements (a login, element names are a guess) they are recorded in plaintext as `username`/`password`.
- Writes echo the request header and carry only an XML document (reply layout is a guess; it was not captured). `status` is `success` for `queryBasicCfg`, which returns a device description (model, firmware, serial, MAC; the serial and MAC are random per process) and `fail` for every other operation. Logins never succeed.
- A bad magic, a length below 16 or above 64 KiB ends the session (`endReason` `read_error`); the bytes read are kept as a read frame (`truncated` for an oversize length). A session holds at most 16 requests (`endReason` `max_frames`).

tcp/6036 is routed here by rule; non-NVMS traffic on it falls back to `tcp`. On any other port the `tcp` catch-all routes a frame (magic plus a plausible length) here.
