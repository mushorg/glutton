# `ftp` decoded data

Transport: TCP. Shared encodings and frame fields are described in [Logging and producers](../logging.md#decoded-data).

**`decoded`:** Array of per-direction frames: `direction`, `command`, `path`, `username`, `password`, `status`, `payload`, `payload_hash`, `truncated`, `server_name`

FTP is served plaintext on tcp/21 and as implicit FTPS on tcp/990 (rule `tls: true`). On 990 the sensor terminates TLS before the handler runs, so the frames are the decrypted FTP dialogue (starting with the `220` greeting) and the TLS details (SNI, JA3/JA4, ClientHello) are in the event's `tls` field and `tls` in its handler stack, not in frames. A 990 client that drops during the handshake produces an event with empty `decoded` (`null`) and the raw client bytes as `payload`. The `STOR` data connection stays plaintext. On a plaintext connection (tcp/21), a TLS handshake record where a command is expected (a client that reads the banner and then sends a ClientHello) or a successful `AUTH TLS`/`AUTH SSL` (`234`) makes the handler terminate TLS itself: it adds a read frame with `command` `tls`, `server_name` (SNI) and the raw ClientHello as `payload` (`truncated` if capped), sets the event's `tls` field and `tls` in the handler stack, and continues the dialogue decrypted. After a bare ClientHello it sends the `220` greeting again; a failed handshake ends the session after that frame. `command` is the upper-cased FTP verb, and only when the first token is 1–8 ASCII letters: binary input keeps `command` empty and stays in `payload`. STOR/RETR/CWD set `path`. Replies: `USER` → `331`, `PASS` → `230` (every login succeeds), `PORT` → `200`/`501`, `SYST` → `215`, `PWD` → `257`, `CWD`/`CDUP` → `250`, `TYPE`/`NOOP`/`PBSZ`/`PROT` → `200`, `QUIT` → `221` and close; RFC 959 verbs that are not emulated (`PASV`, `LIST`, `RETR`, `FEAT`, …) → `502`, an unknown `AUTH` mechanism → `504`, and anything else (unknown verbs, binary) → `500`. Lines under 4 characters are recorded but not answered. `USER` sets `username` and `PASS` sets `password`. Writes set `status` to the numeric reply code. `STOR` connects back to the address from the last `PORT` (active mode only) and stores the first read (up to 1 KiB) under `payloads/ftp/`; its read frame carries those bytes and their `payload_hash`. `STOR` without a valid `PORT` gets `425`, and a malformed `PORT` (not six numbers 0–255) gets `501`. A command line longer than 8 KiB keeps its first 8 KiB in `payload` and sets `truncated`; the rest of that line is dropped. A connection keeps at most about 1000 frames; then the event is produced with `endReason` `max_frames`.
