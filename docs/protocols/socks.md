# `socks` decoded data

Transport: TCP. Shared encodings and frame fields are described in [Logging and producers](../logging.md#decoded-data).

**`decoded`:** Array of per-direction frames: `direction`, `command`, `path`, `status`, `version`, `host`, `port`, `user`, `password`, `methods`, `payload`, `payload_hash`, `truncated`, `requests`, `distinct_requests`, `request_line`, `user_agent`, `http`, plus TLS ClientHello fingerprint fields (`sni`, `ja4`, …) on `tls-clienthello` reads and `error` on a failed `tls-handshake` write

SOCKS4, SOCKS4a and SOCKS5 (tcp/1080, 4145, and any port via the catch-all peek). Read `command` is `socks4-connect`, `socks4a-connect`, `socks4-bind`, `socks5-greeting` (`methods`), `socks5-auth` (`user` and `password`), `socks5-connect`, `socks5-udp-associate`, `tls-clienthello` (tunneled TLS hello after a granted CONNECT), or `tunnel` (plaintext bytes through the tunnel, or the HTTP request after the handshake). `path` is the requested `host:port`. Writes repeat the `command` and set `status` `granted`, `rejected`, `no-auth`, `user-pass`, `no-acceptable-method`, or `tls-handshake`. A SOCKS4a request that stops after the userid (some checkers send the hostname in a later segment, or never; Ochi event b53eecbe-20f7-4fdc-84ea-0a530f6f9833) is granted after one second with an empty `host`, `path` `:port` and `truncated` set on the read frame.

CONNECT is always granted with BND.ADDR `0.0.0.0` (never the sensor address) and a high BND.PORT. Nothing is dialed or forwarded. After the grant, a complete TLS ClientHello in the tunnel is terminated with a self-signed certificate whose CN and SAN match the ClientHello SNI (or, if SNI is absent, the CONNECT host); empty/invalid names fall back to `CN=localhost` (event `tls` object set). A following HTTP request, or a plaintext HTTP request in the tunnel, is handed to the HTTP handler (see below); requests it has no route for get a fixed JSON body reporting documentation IP `198.51.100.10` so open-proxy judges (httpbin `/ip`, `api.ipinfo.io`, `ipv4.icanhazip.com`, …) that check the hostname can complete their check. Non-HTTP tunnel bytes are stored and the session closes.

A `tunnel` read that holds HTTP/1.x requests also sets `requests` (complete request lines in the captured bytes), `distinct_requests`, `request_line` (the first one) and `user_agent` (first one seen), so a client that pipelines the same request many times shows its volume without storing each repeat. A request line cut by the capture cap is not counted, so `requests` is a lower bound when `truncated` is set. The stored payload and `payload_hash` still cover the raw captured bytes. The event's `scanner` is `socks-http-flood` for the known flood recognized by its CONNECT payload hash (a behavioral label that matches only that target; Ochi event f87615a7-3f26-4df7-9c4b-a76c3cd90dec).

HTTP in the tunnel is not stored and answered by `socks` itself: when the captured read is complete (not `truncated`), the bytes are replayed through the HTTP handler (`protocols/tcp/http.go`), so each pipelined request is decoded and answered. The `tunnel` read frame carries an `http` array with the HTTP handler's frames (`parsedHTTP`: reads with `command`, `path`, `query`, `host`, `user_agent`, detector results such as `log4shell` or `citrix`, and writes with `status` and `payload`). There is no separate `socks` write frame for these replies; the `http` writes are the replies. The event stays a single `socks` event, and HTTP session grouping (cookie or source host) is off inside a tunnel so tunneled requests never merge into direct HTTP events. The tunnel conn is not read again after the capture, and an HTTP session inside a tunnel never hands off to MCP. A `truncated` read (a flood past `max_tcp_payload`) is not handed off and gets no reply; only the `requests` summary above describes it.
